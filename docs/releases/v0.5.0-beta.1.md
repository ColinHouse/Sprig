# Sprig v0.5.0-beta.1

Sprig **v0.5.0-beta.1** is the first Beta SDK for trying ordinary JVM
applications, tools and automation with a statically typed Sprig front end and
direct access to selected Java APIs. It is an experimental Beta, not a promise
of production stability or a frozen API. The compiler is **0.5.0-beta.1**;
the language version remains **0.8-dev**. JDK 17+ is required. Linux and macOS
are release-supported; Windows remains an experimental, non-blocking preview.

## Why Beta

The published Alpha established the language and stage-0 compiler. The current
SDK now includes an integrated project workflow for resolving and inspecting
dependencies, running project tests, querying compiler and JVM APIs, reusing
Java libraries, and building ordinary applications with first-party libraries.
The bilingual onboarding course and extracted-SDK checks exercise those paths
using the SDK itself. This is enough for external users to try real projects and
report friction without implying that every Java API or platform is supported.

## Highlights

### Agent-oriented tooling

- `sprig test` runs ordinary Sprig test programs in isolated JVM processes and
  checks compile-fail fixtures by stable diagnostic code.
- `sprig capabilities`, topic help, `sprig explain`, and `sprig api` expose
  implemented syntax, safe repair guidance, Java signatures, project/module
  exports, dependency state, and resolved Sprig API information as JSON.
- `sprig wrap` generates checked, editable Sprig wrappers for supported Java
  APIs; unsupported members include structured reasons.
- `sprig build --emit-java-only` makes generated Java inspectable without
  invoking `javac`.

### JVM interop

- Explicit concrete Java generic arguments, opaque array pass-through, byte
  array helpers, and explicit Java collection adapters cover common boundaries.
- `conform Class to ImportedInterface` checks a bounded foreign interface
  contract without synthesizing adapter methods.
- `sprig api` and wrapper generation share the compiler's JVM member
  classification. Unsupported wildcards, varargs, arbitrary Java SAM
  conversion, arrays as source types, and other shapes remain explicit limits.

### Application foundation

- The bundled `@std` modules cover UTF-8 files and paths, arguments and process
  results, text, UTC time, typed JSON, and test helpers.
- First-party `sprig-cli`, `sprig-http`, `sprig-json-codec`, `sprig-sqlite`, and
  `sprig-web` libraries support command-line tools, HTTP clients and servers,
  JSON applications, SQLite persistence and web APIs.
- Packaged examples include configuration summaries, a Task Tracker, a ledger,
  SQLite migrations, web applications, agent tools, and a bounded frontend
  analysis showcase.

### Package management

- `sprig add`, `sprig remove`, `sprig resolve`, `sprig deps --json`, and
  `sprig project --json` manage project-local packages and explain the resolved
  graph.
- Dependencies can use local paths, Git branches/tags/full revisions and
  repository subdirectories, plus exact Maven coordinates and transitive JARs.
  Schema-4 locks record deterministic graph and checksum evidence; offline
  checks use verified caches.
- Sprig has dependency management but no central package registry or publishing
  service.

### Correctness and onboarding

- The compiler reports structured diagnostics with source ranges and stable
  codes. Regression coverage includes checked numeric operations, JVM bridges,
  dependency locks, installer boundaries and archive extraction.
- The website has bilingual beginner tutorials and an Agent workflow guide. The
  local Task Tracker example exercises file, JSON, argument and error handling
  without a network service or third-party package.

## Dogfood evidence

Maintainer-reported early dogfood with a lower-cost coding model found that the
application layer required little language-level repair. This is anecdotal, not
a controlled benchmark; there is no equivalent Java control implementation,
and the JVM/Fabric host mechanics still required substantial explicit Java and
build-tool work. No productivity or language-superiority claim is made.

## Upgrade from v0.4.0-alpha.1

On a managed Linux/macOS installation, run `sprig upgrade --check` and then
`sprig upgrade`. The installer verifies the published checksum and archive
before switching SDKs; older installed versions remain available. A manual
installation can use the Beta [release page](https://github.com/ColinHouse/Sprig/releases/tag/v0.5.0-beta.1)
ZIP and its `.sha256` file.

Projects created with the Alpha may contain older lockfiles. From each project
root, run `sprig resolve` to regenerate the lock against the Beta SDK before
using `check`, `build`, `run`, `api`, or `test`. The first Maven resolution may
need network access; later operations can use the verified cache with
`--offline`. The release adds tooling and JVM support without an intentional
language syntax redesign, but correctness fixes may diagnose programs that
previously passed because of a compiler defect. Re-run project checks and tests.

## Known limits

- This is an experimental Beta, not production-ready software or a guarantee of
  source, binary, or API stability.
- Windows is not release-supported. Registry publishing/authentication,
  language-server services, generic inference, variance, inheritance,
  self-hosting, and arbitrary Java wildcard/varargs/SAM interop are not
  implemented.
- Java reference results are conservatively nullable. Java arrays are opaque
  boundary values; Sprig has no array source type. Some Java libraries require
  explicit glue or are not yet callable.
- Numeric types and checked integer operations do not prove scientific
  algorithms stable, correctly conditioned, unit-safe, or reproducible across
  all JVMs.
- A green test suite covers the documented contracts and tested workflows; it
  does not prove every application correct.

See `docs/KNOWN_LIMITATIONS.md`, `docs/FEATURE_STATUS_IMPLEMENTED.md`, and the
versioned output of `sprig capabilities --json` before relying on a particular
feature.
